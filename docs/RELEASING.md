# Releasing BLEX

An explicit request to release starts one workflow. The workflow verifies the main commit, builds and tests one candidate image, then publishes that same image and creates its Git version tag. No release branch, candidate Git tag, or separate environment approval is required.

## Release entry point

Use the **Release** workflow in [BUILD.yml](../.github/workflows/BUILD.yml), dispatched on `main`:

```sh
gh workflow run BUILD.yml --repo baealex/BLEX --ref main
```

The optional `version` input accepts `MAJOR.MINOR`, without `v`. With no input, the workflow reads the major from the root `package.json` and selects the minor after the highest existing Git version tag in that major. A major with no releases starts at minor zero. To choose a version explicitly, append `-f 'version=<major>.<minor>'`, replacing the placeholders with the requested numbers.

Existing Git tags remain release history. They are generated by the workflow after verification; pushing a Git tag no longer starts a build. No package version edit is needed for each minor release.

## What the workflow does

1. Run the same application checks as PR/main CI through the reusable [CI workflow](../.github/workflows/CI.yml): release automation tests, dependency audit, server tests, Prisma validation, translations, lint, type checks, client tests/build, and entry budgets.
2. Fix the release version and the dispatch commit SHA. Reject an existing version, a different package major, or a version older than the latest release.
3. Build the AMD64/ARM64 candidate once and store it under the existing Docker commit-SHA tag. This candidate is publicly accessible in the Docker Hub repository, but has no official version tags yet.
4. On native AMD64 and ARM64 runners, pull the candidate by digest, check FFmpeg and first startup with 512 MiB, run the browser smoke test, and scan image vulnerabilities. Both architectures must pass.
5. Publish that exact digest as `baealex/blex:<version>`, `baealex/blex:<major>`, and `baealex/blex:latest`. Verify all three tags and then create `v<version>` on the tested Git commit. Publication does not rebuild the image.

The workflow pins its commit and digest; later main commits do not change the release target. Releases are serialized and an active release is not canceled by another dispatch. Only the publishing job can write Git tags. A failed application, runtime, browser, or security check prevents the publishing job from running.

## Agent procedure

When the user explicitly asks to release BLEX:

1. Read this guide and inspect the current remote main and release tags. A release publishes the committed main version; uncommitted work and other branches are outside that target.
2. Check for an active `BUILD.yml` run before dispatching. Monitor an existing request rather than starting the same release twice.
3. Use the requested version, removing a leading `v` before passing it as input, or let the workflow choose the next minor automatically. State the target repository and release line in the progress update. The release request authorizes the workflow's normal candidate image upload, official Docker tags, and Git version tag; continue through successful publication without asking the user again. It does not authorize source commits/merges, NAS deployments, deletion, or moving existing Git version tags.
4. Dispatch the workflow on main. Identify the new manual run with `gh run list --repo baealex/BLEX --workflow BUILD.yml --event workflow_dispatch`; record its actual `headSha` and run ID.
5. Monitor it with `gh run watch <run-id> --repo baealex/BLEX --exit-status`, giving progress updates during long builds. A successful dispatch is not a completed release.
6. Confirm the publishing job succeeded and the resulting Git tag points at that run's commit. Report the version, commit, image digest, and workflow URL.

If a check fails, report the failing stage and logs. If publication fails after some tags were written, rerun **failed jobs** in the same run (`gh run rerun <run-id> --repo baealex/BLEX --failed`) so the prepared version and tested digest are retained. Matching existing version tags are accepted; different commit/image targets are rejected. Do not create a new release version to hide a failure or automatically roll back/delete published tags.

## Verifying workflow changes

Release orchestration tests run without Docker, registry access, or GitHub writes:

```sh
node --test .github/scripts/release.test.mjs
```

Also lint the workflows with actionlint. Do not dispatch the Release workflow merely to test its configuration: a successful run publishes a real release.
