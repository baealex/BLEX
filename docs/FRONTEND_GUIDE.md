# Frontend Guide

BLEX renders pages with React on the server and uses a shared TanStack Router application for browser navigation. The React screens, settings, admin settings, search, sign-up, and the post editor, come from the server screen host and render in the same application tree.

## Code layout

| Area | Location |
| --- | --- |
| Shared app document, frame, and navigation | `packages/client/src/application/` |
| Public layout, theme, and styles | `packages/client/src/appearance/` |
| Login and reader interactions | `packages/client/src/features/auth/ui/`, `packages/client/src/features/engagement/ui/` |
| Web host and browser configuration | `packages/server/src/application/screen-host/` |
| Client routes, where each URL is a file | `packages/client/src/routes/` |
| Types for the data each server-rendered page receives | `packages/contracts/src/` |
| Screens and feature code | `packages/client/src/features/<domain>/` |
| Shared UI primitives | `packages/client/src/ui/` |
| Tiptap editor | `packages/client/src/features/editor/tiptap/` |

The client package produces two builds under `packages/server/dist/`: `client` for the browser, served at `/assets/ui/`, and `ssr` for the views the server renders. The browser build holds the public entry points and the React screens, so screens share one React, Lingui, and TanStack instance with the application. The application entry imports the screen runtime, `src/screen-runtime.tsx`, only on a screen page, and the build stops there when it checks what public pages load. Every module that public pages load keeps the chunk it would have without screens: the build bundles the public entries once on their own, leaving the screen runtime out, and groups modules the same way, and a module that screens share with a page entry or lazy module moves to a shared chunk beside it.

Public pages and React screens share the theme, prose, and syntax styles in `packages/client/src/appearance/`. `packages/client/styles/main.scss` adds screen-document scrolling, media transitions, and print rules.

## Routes

Add a client URL by adding a file under `packages/client/src/routes/`. A `*.page.tsx` file renders on the server and ships no JavaScript of its own: its server route loads the data and calls `renderPage` with the file's path as the id, and `packages/contracts/src/pages.d.ts` types those props. Any other route file is a browser route. Keep browser route files thin: they declare the path, access guard, and lazy page, and the page itself lives in `features/<domain>`. The Vite plugin regenerates `src/routeTree.gen.ts`; commit that file and do not edit it by hand.

The post detail, home, liked posts, tag list, tag, author, series, static, 404, 403, Developer API quickstart, sign-in, sign-up, first administrator setup, identity check, and password reset pages render in the main React tree, as do a post's revision history, writing timeline, and share links, and the search page the server renders when the screen host is off, as in read-only mode: `features/posts/post-page.tsx`, `features/discovery/discovery-page.tsx`, the `features/authors/author-*-page.tsx` route modules, `features/discovery/search-page.tsx`, `static-page.tsx`, `not-found-page.tsx`, `forbidden-page.tsx`, `features/developer-api/quickstart.tsx`, `features/auth/ui/login-page.tsx`, the `signup-page.tsx`, `setup-page.tsx`, `reauthenticate-page.tsx`, and `password-reset-page.tsx` modules beside it, and `features/posts/revisions-page.tsx`, `timelapse-page.tsx`, and `share-links-page.tsx` render on the server and hydrate in the browser. Their data is a JSON script directly under `<body>`, built field by field in `post-page-data.ts`, `discovery-page-data.ts`, `author-page-data.ts`, `content-page-data.ts`, `quickstart-data.ts`, `login-page-data.ts`, `form-page-data.ts`, and `management-page-data.ts`. Everything there is public in the HTML. Authored HTML, such as a post body, an introduction, a series description, a static page with its stylesheet, or a revision's or timeline frame's content, stays out because hydration reads it from the server markup, and so does the owner's introduction Markdown, which their editor's textarea already holds. The sign-in and account forms carry only their form models, including the visitor's own CSRF token, and read their footer back from the server markup. The setup token and the password reset link stay out of the data too: the browser reads them back from the server form, which already posts them. The post management pages reach only the post's author, so they carry the author's own CSRF token for their forms.

Each author route, the search page, static page, error page, the quickstart, the sign-in page, each account form, and each post management page loads only its own module. These forms, and the revision and share link forms, keep what was typed before their code arrives, and if that code fails to load, the server form still submits. When the post, author, sign-in, account form, or post management page's code fails to load on a direct visit, its server markup stays in place with any typed text and open menus, and links in it load full pages. On the sign-up form, the application loads hCaptcha in explicit mode through `features/auth/ui/hcaptcha.ts` and draws the widget once hCaptcha's onload callback reports the API ready, sometimes before hydration, so React leaves that element's contents alone. The sign-up screen draws its widget through the same loader, and no document loads hCaptcha by itself. `GET /sign` shows the sign-up screen from the screen host; this server form answers after a form post to `/sign` fails. The owner's inline introduction editor hydrates in its own Suspense boundary once its code arrives. On the introduction edit page, `features/authors/about-draft.ts` runs with the application entry: it restores a saved draft, holds hydration while a Hangul syllable is being composed, and accepts Save before the editor code arrives. If that code fails to load, the page keeps the writer's text and offers a retry that keeps it in the tab.

The login prompt and the one-time Telegram notice render in the application tree from `application/prompts.tsx`, on every application page, even when the page's own module did not load. The login prompt opens from a capture-phase click listener because React holds clicks inside a page whose code has not loaded. The toaster renders there too: `utils/toast.tsx` loads it with a screen's first toast, inside its own error boundary, and it stays across pages so a toast outlives the move that follows it. A toaster that fails to load or render loses only its toasts.

The work log pages render in the main React tree too: `features/work-logs/index-page.tsx`, `detail-page.tsx`, `delete-page.tsx`, and `shared-page.tsx` each load only their own module, from data built in `page-data.ts`. What the writer wrote, such as log titles, entries, and share headlines, stays out of the data because hydration reads it back from the server markup, and ids appear only where the page already shows them in a link, form, or media address. A shared log is public, so its data carries no CSRF token. The forms keep what was typed before their code arrives and still submit if it fails to load. The chosen attachment's name and the new share link's copy button are React handlers.

Screen pages render in the main React tree as well, but on the client: the screen host sends a loading status in the screen's place and the page's data in `blex-screen-page-data`, and the application hydrates the status as it is. The screen runtime then checks that data, loads the screen's module and its messages for the page's language, and builds the page content with the screen inside `StrictMode`, an error boundary, Lingui's `I18nProvider`, and a React Query client persisted in session storage. Its cache key comes from the viewer in the screen data, not the previous page, and caches of other viewers, languages, and time zones are removed when the first screen of a page load restores. Signing out removes the signed-in viewers' caches and keeps a signed-out visitor's: the site script removes them when the header's sign-out form submits, natively or through the application, or when account deletion signs the viewer out, and again when the next page shows signed out or the document is left, because an open screen can still save its cache until then. These load with the runtime, so public pages do not carry them. After a move inside the application, a screen that loads within three seconds replaces the previous page directly; a slower one shows the loading status first and replaces it when it arrives. A screen that cannot load or render shows its error in place, and the header and links keep working. Screens take the viewer, the viewer's time zone, and the sign-up form's settings from that data and props; the application sets nothing on `window` for them, and resource paths are fixed in `modules/static.module.ts`. A screen document also names `/assets/blex/screen.js` in a `nomodule` script that browsers skip: an application from before this change imports it on its way to a screen, and it reloads that tab.

## Pages and browser behavior

- Use `renderApplicationDocument` from a `*.page.tsx` file for pages in the main application so direct visits receive server-rendered HTML and internal navigation uses the app router.
- Include the initial content and metadata in the server response. Avoid a second browser request for data already needed to render the page.
- Initialize browser features when their route loads. Remove event listeners, disconnect observers, and destroy editor instances when navigating away.
- Moves within the application do not fire `beforeunload`. A screen that warns about unsaved edits also blocks the shared `window.blexHistory`, and returns its warning from `enableBeforeUnload` so the application leaves form posts to the browser while it applies.
- Keep browser-only APIs out of server render paths. Load large editor and interaction modules when the relevant screen needs them.
- Keep forms, focus, keyboard navigation, loading feedback, and error states usable. Check direct visits, internal navigation, and back/forward behavior.
- `appearance/site-client.ts` answers the site menus, the theme button, and the header search box's Esc and Cmd/Ctrl+K in the capture phase, before and after the page hydrates. The search box reports when it hydrates and keeps its panel closed if Esc closed it before then; Esc closes its panel through an event the box handles synchronously.

## Components, state, and requests

- Keep props and API boundaries typed. Prefer composition and existing shared controls over new configurable component systems.
- Decode screen-host JSON as `unknown` and validate it with `components/screen-props.ts` before rendering: `parseScreenPage` for the page around the screen and `parseScreen` for its props. Keep the screen name paired with its component props, and update the parser when a screen's inputs change.
- Put shareable filters and pagination in the URL; keep transient form and interaction state local.
- Follow the request pattern used by the code you are changing. The main app uses browser `fetch` and forms; web screens use their existing Axios client, React Query, and form libraries.
- Preserve the runtime's CSRF handling and check API error responses before consuming their bodies.
- React Compiler runs on screen code only. Public page modules stay outside it, and the build fails if public pages load compiled code. Do not assume it is enabled for public pages, or add memoization without a measured need.

## Styling and translation

Use semantic Tailwind tokens and follow the [Design Guide](DESIGN_GUIDE.md) and [UI Change Style Guide](UI_CHANGE_STYLE_GUIDE.md). Keep screen-specific CSS close to the feature.

The server sets the document language from the user preference or site default. Public SSR and browser components use `ui()` with literal English product copy; React screens use the existing Lingui macros. Both use the same PO catalogs. Public pages load only the `ui()` messages, and screens add the rest before they render; the build fails if code that public pages load uses a screen message. The Developer API guide is the one public page with its own part: its macros use `developer.` IDs, and it loads those messages before it renders. Activate the document catalog before hydration and the destination catalog before internal navigation. Resolve translated labels during rendering, never at module initialization. Do not pass authored content through translation helpers or create a separate runtime per feature. See [Translation Guide](TRANSLATION_GUIDE.md) for current coverage and checks.

## Development and checks

Follow the [local development setup](DEV_CONVENTION.md#local-development). `pnpm dev` and `pnpm build` build the public pages and the screens together. `pnpm dev:client` runs Vite directly on port 8100 with its built-in file watcher.

Run `pnpm test` and `pnpm type-check` for changes to the main application. The client type check covers browser code and all Vite/Lingui configuration files. For web changes, use the workspace commands in the [Testing Guide](TESTING_GUIDE.md).
